# Reveal migration — demo notes (2026-05-05)

## Using Astro

We took the WordPress site at revealbi.io and rebuilt it as a static Astro site. The whole thing now lives as files in a Git repo: every page is a Markdown file with structured YAML at the top, and that YAML describes the page as a list of "sections" — a hero, a feature row, a pricing block, a CTA, and so on. We have 27 of these section types, each one a small reusable Astro component, and a single dispatcher (`SectionRenderer.astro`) that reads the YAML and renders the right component in the right order. So instead of WordPress's free-form HTML soup, every page is a clean, validated data structure. There are 55 sectioned pages in English and 55 in Japanese, plus the blog (~107 posts), glossary, customer stories, webinars, and whitepapers — all local, all in the repo, no database. Many of those still need to go through parity checks and will require further work.

## Styling

For styling the solution is hybrid. Anything new uses Tailwind CSS v4. But for the things that would have been painful to re-author and where we wanted pixel-faithful WordPress DNA — the megamenu, the modals, the typography, the fonts — we ported the original CSS straight in, sitting under `src/styles/` (`navigation.css`, `sections.css`, `ig-modal.css`, the vendor bundles, the self-hosted webfonts).

Images were brought over wholesale. About 1,900 files, 191 MB, committed straight into `public/images/` with the exact same folder structure WordPress uses plus topical folders. That meant zero rewriting of image paths in the Markdown content; the URLs match what WP served. Nothing is yet converted to webp and we're not using Astro's built-in image optimization yet — that was a deliberate parity-first call so we wouldn't muddy the WP-vs-built visual diff. It's a clear post-launch performance win waiting on the table — flipping to `<Image>` would give us automatic webp/avif conversion on the whole 191 MB pile.

## Parity checks

To prove that we actually match WordPress visually, my clanker buddy built a parity harness. It uses Playwright to screenshot the live WP page (well, not live — actually scraped and running locally to conserve tokens) and our built page side-by-side at mobile, tablet, and desktop, and dumps them into a gallery for human review. Early on I tried adding pixel-diff math on top of it, but full-page screenshots have a fundamental problem — if our build's section heights drift by even a few pixels, every block below shifts and the diff lights up red across the entire page. So I threw the math out, kept the side-by-side gallery, and review visually. More effort, but better results. I might try to tackle it fully automatically later on. A lot of pages still need to go through parity checks. For the blog items (~107) I have an idea on how to export them through the WP admin panel.

## Translation

For Japanese — and the future Spanish, Korean, Brazilian Portuguese — translation is automated through an n8n workflow. It ingests the English Markdown, runs it through an LLM with our translation rules, and writes the localized file into `src/content/pages/ja/`. The contract for what gets translated and what stays as-is lives in `n8n-contract.md`; the operational troubleshooting log is `n8n-knowledgebase.md` — five recorded failure modes and their fixes, plus the playbook for re-running. Localized routes work through `src/pages/[lang]/index.astro` and a dynamic page route that fall back to English if a locale is missing a page. Internal-link rewriting is centralized in a single helper which the header, footer, and demo modal all use. Japanese is the only locale fully populated end-to-end so far; the rewriter is locale-agnostic, so es/ko/pt-BR will Just Work when n8n is pointed at them. While I was working on that I found out about a potential alternative solution for translations — more on that in the CMS section.

## Lead capture and integrations

Lead capture is the part I want to be especially clear about, because it's the highest-stakes piece for marketing. We did not rewrite the lead pipeline. The forms themselves — the embedded "Request a Demo" form and the global modal — are plain HTML in two Astro components, with the same field names, classes, and reCAPTCHA wiring WordPress used. The actual submission logic is two vendored JavaScript files (`leadTracker.js`, ~780 lines, and `sf.common.js`) loaded globally from the layout. They post to the same Infragistics backends WordPress posts to today: lead submissions to `acctapis.infragistics.com`, tracking events to `infragistics.com/api/leadtrackingevents/track`, whitepaper downloads to `/api/productresources/...`, reCAPTCHA to Google. Staging vs production is auto-detected by hostname, and the host can be overridden via a `PUBLIC_LEAD_API_BASE` env var if Salesforce ever wants us pointed somewhere new. The only Astro-side glue is a small `window.__REVEAL_CONFIG__` object the layout injects on every page so the vendored scripts can read environment-specific URLs without us modifying them. From Salesforce's perspective, from GA's perspective, from the marketing ops perspective — nothing changes on cutover day. Same wire format, same endpoints, same enhanced-conversion datalayer pushes.

One thing landed today on this front: when I went to verify the forms, I discovered that `leadTracker.execute()` was never actually being called anywhere — all 6 lead forms across the site (industry-page demo, footer newsletter, header demo modal, pricing-quote, whitepaper download, request-demo body) were silently dead. Each one is now wired via a per-form init script that mirrors WordPress's settings template (tier, product code, lead type). reCAPTCHA v3 is plumbed and env-gated — script only loads when `PUBLIC_RECAPTCHA_SITE_KEY` is set, and forms still submit gracefully if it isn't. We do need to test this thoroughly on staging before cutover.

## CMS

For the marketing team's day-to-day editing, I picked Sveltia CMS. Originally I spent time on Keystatic but had to back it out because of some technical hurdles between its format and the one n8n expects. Authentication will happen through an OAuth app in GitHub and users will work directly on the repo. I believe we can also have admin locks for certain sections of the website.

As of today, the local-dev workflow is feature-complete: I can open `localhost:4321/admin/` in Chromium, pick the repo root via the browser's File System Access API, and edit any of the 55 EN pages with a structured form per section type. There are also four read-only collections for the non-English locales (Spanish, Japanese, Korean, Portuguese-BR) so editors can browse the translations without accidentally editing them — n8n owns those files. A CI guard catches accidental cross-locale commits. The remaining piece, GitHub OAuth for non-developer access, is deferred until someone other than me actually needs to edit through a browser they don't control.

Now here's something about translations that Sveltia supposedly can do — Sveltia gives editors a forms UI to edit each language's Markdown files (English, Japanese, etc.) side by side in the repo, and if we wire a custom widget to a translation API (OpenAI or our existing n8n webhook), it becomes a one-click "translate this field" tool right inside the CMS, on top of the bulk n8n workflow that auto-generates whole localized files from English. We can also have pages marked as "untranslatable" with intent. Still exploring that option.

## Search

Search is handled by Pagefind. It's a static-site search engine — it indexes the whole site at build time and ships the index as static files. No search server, no Elasticsearch, no Algolia subscription, no database. Search just works the moment `dist/` is deployed to a CDN.

## Infrastructure and deployment

Stack-wise, the build chain is `npm run build` → content validation → `astro build` → Pagefind for full-text search. The output is just `dist/` plus `public/` — deployable to any static host, no Node server, no PHP, no database. Analytics (GA4, GTM, LinkedIn, Meta, Hotjar, HubSpot) are all wired through environment variables and lazy-loaded so they don't drag down the page if a key isn't set.

Right now, the site lives in a GitHub repo. Every push triggers a GitHub Actions build that syncs the output to an S3 bucket served by CloudFront. Big thanks to Pete for setting up the entire infrastructure. The build itself takes about a minute end-to-end.

The only remaining external dependency before we can flip analytics on in production is a handoff from marketing: the GA4 measurement ID, the GTM container ID, the LinkedIn partner ID, the HubSpot portal ID, and the reCAPTCHA v3 site key. Every snippet is already wired and gated on those env vars — the moment they land in the prod `.env`, everything activates automatically. No more code changes required on our side.

## Replicating this on another WordPress site

The interesting thing is that most of what I just walked through is now reusable. If Infragistics wanted to migrate another WP site — Slingshot, Indigo.Design, the main `infragistics.com`, anything on the same stack — most of the heavy lifting carries over.

What's reusable as-is:
- **The whole component library and dispatcher pattern.** 27 section types — heroes, feature rows, pricing teasers, comparison tables, FAQs, lead-capture forms — drop into a new site without modification. The Zod schema and `SectionRenderer` come along for the ride. New sites that need a section we don't have add it once and benefit everyone.
- **The build, parity, and deployment chain.** Astro config, content validation, Pagefind indexing, the Playwright parity harness, GitHub Actions → S3 → CloudFront — all of it is repo-level boilerplate. New site = new repo from a template.
- **The translation pipeline.** The n8n workflow, the translatable-keys contract, the locale-fallback router, the link-rewriting helper — the same machinery handles any new site, you just point n8n at a different repo.
- **The lead-capture wiring.** Same `leadTracker.js` + `sf.common.js`, same `__REVEAL_CONFIG__` injection, same env-gated analytics. Forms post to the same Salesforce endpoints, so marketing ops sees zero change across sites.
- **The CMS.** Sveltia is just a `config.yml` referencing the schema; clone the pattern, swap the collection names.

What's new-site work, but cheaper the second time:
- **Content extraction.** Each WP site has its own HTML quirks — different theme, different lazy-load convention, different inline styles, different megamenu plugin. We've already cataloged the failure modes (`b-lazy` collapse, inline `<style>` blocks, form-spinner stripping, broken image-path placeholders) so the second site's extractor reuses the patterns instead of discovering them.
- **Branding port.** Their fonts, their megamenu CSS, their brand colors, their hero shapes. Mechanical, not creative — the structure already exists.
- **Per-page parity walk.** Every site needs eyes on every page. But the harness, the workflow, and the tracker template are all there.

Realistically: the first site (this one) took the long path because we were inventing the architecture as we went. A second site on the same stack should be a fraction of the effort — the hard problems (n8n contract, lead-capture preservation, parity tooling, deploy pipeline) are solved. What's left is content extraction and visual sign-off, both of which we now have a repeatable playbook for.
