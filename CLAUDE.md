## Project Orientation

This repo is the **Reveal Embedded Analytics marketing site** — a static Astro 6 rebuild that replaced the legacy WordPress site. It is **live in production** at `www.revealbi.io` (AWS S3 + CloudFront). The legacy WordPress site is retired to `old.revealbi.io`. A noindexed staging copy runs at `astro-staging.revealbi.io`.

`README.md` is the full architectural reference — read it for anything not covered here. This section is the fast map.

### Stack
- **Astro 6** (`output: 'static'`, no SSR adapter) — pure static build.
- **Tailwind CSS v4** via `@tailwindcss/postcss`, coexisting with ported WP CSS in `src/styles/` (parity).
- **Frozen WP jQuery bundle** (~5,800 lines, 14 files in `public/js/`) — not bundled, not modernized, kept verbatim for visual/behavioral parity. Do not "clean up" these files.
- **Sveltia CMS** (browser-based, File System Access API) at `public/admin/`.
- **pagefind** search, built during `npm run build`.
- **n8n → Ollama (`gemma4:31b`) → GitHub** translation pipeline (`n8n/ja-translation.json`).
- Hosting: **AWS S3 + CloudFront**, auto-deployed by GitHub Actions per branch.

### Architecture — the one pattern that matters
The site is a **section-dispatcher**. Every page lives at `src/content/pages/<lang>/<slug>.md` as YAML frontmatter with a `sections: []` array (empty body). `src/components/SectionRenderer.astro` maps each `section.type` → a component in `src/components/sections/`. The schema is a `z.discriminatedUnion('type', […])` over ~63 section types in **`src/content.config.ts`** (note: at `src/`, NOT `src/content/config.ts`).

Translatable fields are annotated in the schema with `t()` / `tHtml()` / `asset()` describe-helpers; these drive `dist/translatable-keys.json` (from `src/pages/translatable-keys.json.ts`), which the n8n pipeline consumes. Adding a section type or translatable field is a one-line schema change that propagates to translation automatically.

### Where things live
- `src/content/pages/{en,es,ja,ko,pt-BR}/` — 72 EN pages; 67 each for ES/JA/KO/PT-BR (auto-generated by n8n; EN is source of truth).
- `src/content/{blog,glossary,stories,whitepapers,webinars}/` — blog (109 EN + locale translations), glossary (24), stories (10), whitepapers (21), webinars (55). Glossary/stories/whitepapers/webinars are EN-only.
- `src/components/sections/` — ~64 section components. `src/components/ui/` — Header, Footer, DemoModal, GdprBanner, Card, header/*.
- `src/lib/` — `href.ts` (locale-aware link rewriting, `localizedHref()`), `env.ts`, `blog.ts`, `blog-authors.ts`, `render-markdown.ts`, `seo.ts`, `whitepaper-i18n.ts`.
- `src/i18n/` — `{en,es,ja,ko,pt-BR}.yml` chrome strings + `index.ts` deep-merge fallback. **EN + JA complete; ES/KO/PT-BR are stubs** (fall back to EN).
- `src/pages/` — routes: `index`, `[slug]`, the five collection index/`[slug]` routes (+ `events`), blog pagination/category routes, `[lang]/*` localized routes, plus dedicated route files for special slugs (`reveal-navigation`, `embedded-analytics`, `in-the-news`, `licenses`, `license-agreements/*`, `pricing/embedded-analytics`).
- `scripts/` — ~39 `.mjs` helpers (content validation, locale/blog extraction, sitemap build, parity tooling).
- `public/images/` (~224 MB) — wholesale WP image port. Newer assets use the CDN at `PUBLIC_CDN_BASE` (`static.infragistics.com/marketing/reveal`).
- `parity-tracking.md` (repo root) + `parity/` — page-by-page parity status and per-page verdicts. **Not** under `docs/`.
- `docs/` — `handoff/`, `n8n/`, `cms/`, `seo/`, `history/`. Index in `docs/README.md`.

### Build & env
- `npm run dev` → `http://localhost:4321`. **WSL note:** node runs on the Windows side, not inside WSL.
- `npm run build` runs: `validate-content.mjs` → `extract-locale-blog-posts.mjs` → `astro build` → `fix-locale-css-refs.mjs` → `normalize-trailing-slash.mjs` → `pagefind` → `build_sitemaps.mjs`.
- Public config lives in committed `.env.staging` / `.env.production` (NOT secrets). `PUBLIC_NOINDEX` is 1 on staging, 0 on prod, so indexing flips with the build target. Prod has GTM + reCAPTCHA live; GA4/LinkedIn/Meta/Hotjar/HubSpot env vars are still empty (each snippet is env-gated and off until filled).
- Trailing-slash / URL routing is handled by **CloudFront Functions in AWS** (not in this repo), plus the `normalize-trailing-slash.mjs` build step.

### Conventions & gotchas
- **EN is the only locale you edit by hand.** `{es,ja,ko,pt-BR}/` page content is n8n-owned; a single commit should not mix EN and a generated locale.
- Don't fabricate image/asset URLs — flag images for CDN upload (`PUBLIC_CDN_BASE`) rather than inventing paths.
- The repo has custom subagents/commands under `.claude/` for parity work (`/audit`, `/refit`, `/convert`) and design-to-page/blog builders. Use them for those tasks.
- CSP is intentionally omitted from the security-headers policy (inline jQuery). Don't add a strict CSP without a dedicated pass.

## Commit Procedure
When pushing changes, always commit to a new branch and open a pull request to staging.
When instructed to push to production, open a pull request to merge staging changes into main (production)
Do not deviate from this defined process.  We do not create direct pull requests into production, we only merge from staging.

## Keeping main and staging in sync
After every staging → main release PR is merged, immediately open a follow-up PR to merge main back into staging. This prevents main from accumulating merge commits that staging does not have.

The pattern is:
1. Feature branch → staging (normal development PR)
2. staging → main (release PR, when ready to deploy)
3. main → staging (sync PR, immediately after step 2 merges)

Step 3 is mandatory. Without it, each release leaves an orphaned merge commit on main that staging never receives, causing the branches to appear diverged even though their file content is identical. Over multiple releases this divergence grows and makes git history confusing.

To open the sync PR after a release:
```
git fetch origin
git checkout -b sync/main-into-staging
git merge origin/main --no-edit
git push -u origin sync/main-into-staging
gh pr create --base staging --head sync/main-into-staging --title "sync: merge main into staging post-release" --body "Routine post-release sync. Brings the main merge commit back into staging so branches stay in lockstep."
```

## Pull Request Updates
Before updating a branch or adding commits to an existing PR, always verify the PR has not been merged or approved with `gh pr view <number> --json state,mergedAt`. Do this check even if you just opened the PR — it may have been approved and merged quickly. If it has been merged, do not push to that branch — create a new branch and open a new PR instead. Pushing to a merged branch adds unnecessary commits and creates confusion.
